## 🟨早期楷體的先天歷史包袱：

全字庫正楷體 (TW-Kai) 及標楷體（DFKai-SB）等這類早期 Windows 95/NT 時代設計的字型，它在字型內部的座標系（EM Square）中，會將中文字的位置刻意畫得偏下（為了配合早期 Windows 的中西文混排視覺）。
而「AR PL UKai TW（文鼎中楷）」等現代設計，則是字身垂直置中。
瀏覽器在繪製同一行文字時，會把所有字型的基線（Baseline, y=0）死死對齊在同一條水平線上。只要兩個字型共用同一條基線，「全字庫正楷體」的筆畫位置天生就比「文鼎楷體」矮了一截，純靠 CSS 的 @font-face 參數是無法垂直平移字形座標的，除非多包一層 span 元素做 transform 偏移。

最根本解決之道是直接修改「全字庫」以對齊新式基準。

## 🟨全字庫正宋體也不倖免

全字庫正宋體 及 新細明體 同樣存在基線偏低、與現代字型混排會有高低差的問題。

### 為什麼全字庫正宋體也有這個問題？

這主要是因為**歷史背景與規格系出同源**：

#### 1. 兩者誕生於同一個時代（1990 年代 CNS 11643 專案）

行政院在早期推動「全字庫」數位化時，正楷體（TW-Kai）與正宋體（TW-Sung）是採用**同一套座標系與字型規格標準**製作的。

#### 2. 對標早期 Windows 系統字型（新細明體 PMingLiU）

- 全字庫楷體（TW-Kai）在設計時，座標系對標的是 **「標楷體 (DFKai-SB)」**。
- 全字庫宋體（TW-Sung）在設計時，座標系對標的是 **「新細明體 (PMingLiU)」**。
- 在早期 Windows 95/NT 的 GDI 渲染架構下，這兩套老字型都把中文字身的幾何位置**刻意往下拉（偏低）**，以迎合當時西文字母下降部（Descender，如 g、y、p）的行高預留空間。

#### 3. 與現代明體/宋體混排時的衝突

如果你以現代數位標準設計的明體為主字型，例如：

- **文鼎 PL 新宋 / 明體**（AR PL UMing TW / AR PL Sung）
- **思源宋體**（Source Han Serif / Noto Serif TC）
- **一點明體**（I.Ming）或 **源流明體**

這些現代字型都嚴格遵循 **「中文字身垂直置中」** 的現代排版標準。因此，一旦主字型缺字退回到「全字庫正宋體」時，缺字一樣會**明顯掉下去、底部不齊平**。

---

## 🟨註：

全字庫不是為了排版而設計，它的目的是提供單字、使中文不缺字，所以會存在單字之間大小不一致的現象。在調整時，不可能要求每個字都圓滿對齊，只能盡量取平均值。
