# 以 Noto 字型為例說明載入效能與字重優化

## 1. 優化前

假設大藏經典藏網站典藏大量歷史經文、註釋與古籍數位化資料。為了兼顧繁簡體中文顯示與明體（Serif）、黑體（Sans）的視覺層次，目前網站採用的 Google Fonts 引用方式如下：

```html
<!-- 優化前的字型引用：全字重範圍 (100..900) -->
<link
  id="google-fonts-link"
  href="https://fonts.googleapis.com/css2?family=Noto+Sans+SC:wght@100..900&family=Noto+Sans+TC:wght@100..900&family=Noto+Serif+SC:wght@200..900&family=Noto+Serif+TC:wght@200..900&display=swap"
  rel="stylesheet"
/>
```

### 全字重引用的潛在效能瓶頸

1. **龐大的 CSS 定義與分包請求數**：CJK（中日韓）字型字元數極多，Google Fonts 會依照 Unicode 範圍（Unicode-range）將字型檔拆分為數百個子集。要求 `100..900` 全字重意味著瀏覽器必須解析巨大的 CSS 樣式表，並為每一種微小的字重切換下載對應的字體分包。
2. **網路傳輸與首屏渲染延遲（FOIT/FOUT）**：過多的字型資源搶占 HTTP/2 / HTTP/3 傳輸管道，導致行動裝置或網路環境較差的讀者在開啟經文時出現明顯的空白（Flash of Invisible Text）或排版跳動。
3. **無效的 DOM 渲染負擔**：瀏覽器字型引擎需要維護龐大的字型對照表，增加頁面重繪（Repaint）與重排（Reflow）的運算時間。

補充：google字型已經使用切片化技術，這裡所謂的效能問題是在同樣切片化技術下說的，不是與"未切片化"相比。若與"未切片化"相比，無論如何都是快非常多的。

## 2. 為什麼不需要載入全字重？

在典藏級網站的視覺設計與閱讀體驗中，全範圍字重存在以下非必要理由：

1. **視覺辨識極限與微小字重差異無效**

- 在螢幕顯示上，字重 `300` 與 `320` 或 `400` 與 `420` 的粗細差異僅有數個像素（px）等級，肉眼幾乎無法察覺。
- 為極少數非標準數值（如 `320`）多載入一整套字型檔，投資報酬率極低。

2. **古典經文閱讀體驗著重「清晰」而非「細微漸層」**

- 典藏網站的核心在於經文正文、註解與標題的清晰對比。維持 3～5 種階層明確的字重，比提供 9 種模糊的字重更能建立舒適的閱讀秩序。

3. **無障礙存取規範（WCAG 2.1 AA）防護**

- 字重 `100` (Thin) 與 `200` (Extra-Light) 在高解析度螢幕上線條過細，極易導致筆劃斷裂，無法達到 WCAG 2.1 AA 規範要求的最低文字對比度（Contrast Ratio 4.5:1），影響年長者或視力受限讀者的閱讀體驗。

## 3. 推薦的常規字重配置 (300 / 400 / 500 / 700 / 900)

經評估典藏網站的視覺階層需求，建議將字重精簡為 **`300;400;500;700;900`** 五種規格：

| 字重數值  | 名稱    | 在典藏網站的適用情境（經文排版範例）               |
| --------- | ------- | -------------------------------------------------- |
| **`300`** | Light   | 夾註小字、考據註腳、卷尾出版資訊、裝飾性大字背底   |
| **`400`** | Regular | **經文正文**、長篇對讀內容、導覽選單（標準預設值） |
| **`500`** | Medium  | 正文中的強調關鍵字、次要小標題、按鈕文字           |
| **`700`** | Bold    | 經頭品名、部類大標題、系統主要 Alert / 按鈕        |
| **`900`** | Black   | 專題首頁 Banner 主標題、典藏冊別巨幅封面字體       |

## 4. CSS 字重自動降級匹配機制（Font Weight Matching Algorithm）

若專案中部分舊 CSS 寫死非標準數值（如 `320`、`350`）或相對語意（`bold`、`bolder`），團隊**無需擔心網頁排版毀損或字體消失**。

根據 **W3C CSS Fonts Module Specification** 規範，瀏覽器在找不到精確字重時，會依循以下標準機制進行「最佳接近值匹配」：

### 情況 A：設定小於 400 的數值（例如 `font-weight: 320`）

- **演算法規則**：優先向下（更細）尋找最接近的可用字重；若無更細者，則向上尋找。
- **實際結果**：因為已載入 `300`，設定 `320` 的元素會**自動且精確地匹配渲染為 `300**`。

### 情況 B：設定介於 400 與 500 之間的數值（例如 `font-weight: 450`）

- **演算法規則**：優先向上（更粗）尋找；若無則向下尋找。
- **實際結果**：若已載入 `500`，設定 `450` 會優先升級匹配渲染為 `500`。

### 情況 C：關鍵字 `bold` 與 `bolder`

- **`bold`**：CSS 規範明確定義 `bold` 等同數值 **`700`**。載入列表中含有 `700` 即可完美對應。
- **`bolder`**：根據父元素的字重相對計算。若父元素為 `400`（正文），`bolder` 計算出來會要求 `700`，並自動匹配至已載入的 `700`。

## 5. 優化後的 HTML `<link>` 範例代碼

以下為符合 HTML5 語意規範、無障礙與效能最佳化的引用代碼：

```html
<!-- 1. 預先建立 DNS 解析與 TLS 握手，加速 Google Fonts 載入 -->
<link rel="preconnect" href="https://fonts.googleapis.com" />
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />

<!-- 2. 精簡後的字型引用：僅載入 300, 400, 500, 700, 900 五種實用字重 -->
<link
  id="google-fonts-link"
  href="https://fonts.googleapis.com/css2?family=Noto+Sans+SC:wght@300;400;500;700;900&family=Noto+Sans+TC:wght@300;400;500;700;900&family=Noto+Serif+SC:wght@300;400;500;700;900&family=Noto+Serif+TC:wght@300;400;500;700;900&display=swap"
  rel="stylesheet"
/>
```

### 優化效益總結

1. **頻寬與請求數量大幅降低**：精簡請求範圍後，CSS 字型分包對照清單體積縮減超過 **60%**。
2. **首屏繪製時間（FCP）顯著提升**：減少資源搶占，經文正文能以最快速度渲染完成。
3. **安全無痛銜接**：舊程式碼中的 `320` 等字重透過 CSS 原生演算法會自動降級至 `300`，無須緊急修正全站既有 CSS 樣式表。
