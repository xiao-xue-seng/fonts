## tag 更新的策略：

- 新增或更新字型時，變更次要版號。
- 更新網站專屬字型清單時，變更第三版號。

### 加上新 Tag 並推送到 GitHub 的方式

```
git tag v1.2.0
git push origin v1.2.0
```

一定要 `push` 才會生效，新手常忘。
(目前這部分只有CLI，大多數軟體/插件都沒有提供UI。)

---

**非常正確！這個策略完全符合 語意化版本號（Semantic Versioning, 簡稱 SemVer）的標準規範。**

在標準的語意化版本號 `MAJOR.MINOR.PATCH`（例如 `v1.2.3`）中，你的規劃正好完美對應這三個層級：

---

### 你的策略與語意化版本對照表

| 版本層級             | 版號變更範例            | 觸發動作（你的策略）                                                                                  | 語意化版本定義 (SemVer)                  |
| :------------------- | :---------------------- | :---------------------------------------------------------------------------------------------------- | :--------------------------------------- |
| **主版號 (Major)**   | `v1.0.0` ➔ **`v2.0.0`** | SDK（`font-loader-min.js`）發生**破壞性變更**（例如參數寫法大改、JSON 結構大改致舊版 SDK 無法解析）。 | 不相容的 API 修改 / 重大重構。           |
| **次要版號 (Minor)** | `v1.0.0` ➔ **`v1.1.0`** | **新增或更新字型檔案**（總清單 `fonts.json` 擴充）。                                                  | 向下相容的功能/資源新增（New Feature）。 |
| **修訂號 (Patch)**   | `v1.1.0` ➔ **`v1.1.1`** | **更新網站專屬字型清單**（例如 `amec.json` 的勾選設定調整）。                                         | 向下相容的微調、配置更新或 Bug 修正。    |

---

### 為什麼這個策略非常優秀？

1. **對 jsDelivr `@v1` 完美相容：**
   無論你更新的是**次要版號**（`v1.1.0`）還是**修訂號**（`v1.1.1`），對 jsDelivr 的 `.../fonts@v1/...` 網址來說，它都會自動捕捉並指向最新的 `v1.x.x` Tag。你的外部網站 HTML 完全不用改動。

2. **版本紀錄（Git History）非常清晰：**
   團隊或你自己在看 Git Tag 紀錄時，一看到版號跳動就能立刻判斷這版 Release 做了什麼：
   - 看到 `v1.2.0`：就知道「這個版本新增或改動了字型庫資源」。
   - 看到 `v1.2.1`：就知道「這個版本只是某個網站調整了專屬字型勾選清單」。

3. **保護正式環境：**
   只有當未來有一天你改寫了 SDK 腳本，且**會導致舊有網站無法載入**時，才需要開闢 `v2.0.0`（此時正式網站仍停留在 `@v1`，完全不會被壞掉的新 SDK 影響）。
