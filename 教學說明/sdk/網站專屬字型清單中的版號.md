🟨Q：在給amec網站用的專屬字型清單中，字型引用的網址用 `...fonts@main/` 或 `...fonts@v1.2.0/` 哪種較好？

---

答案是：在**正式生產環境（Production）**，強烈推薦使用具體版本號 **`@v1.2.0`**（或主版本號 **`@v1`**）！

但在**開發測試階段**，可以使用 **`@main`**。

以下為您分析兩者的優缺點，以及為什麼正式環境一定要用版本號：

---

### 一、 兩種網址寫法的詳細對比

| 比較項目         | 使用 `@v1.2.0` (具體版本號 Tag)                                                      | 使用 `@main` (Git 分支)                                               |
| :--------------- | :----------------------------------------------------------------------------------- | :-------------------------------------------------------------------- |
| **CDN 快取效能** | ⚡ **極速（永久快取）**<br>jsDelivr 會將具體 Tag 視為不可變檔案，全球 CDN 秒級回應。 | 🐢 **較慢（需檢查更新）**<br>jsDelivr 會頻繁確認分支是否有新 Commit。 |
| **更新即時性**   | 瞬間生效（發布新 Tag 即生效，不需要 Purge CDN）。                                    | 遲緩（jsDelivr 最長會快取 7 天，更新後需手動 Purge）。                |
| **線上穩定度**   | 🛡️ **100% 安全**<br>絕不會因為您在 GitHub 不小心改壞程式碼而導致正式網站崩潰。       | ⚠️ **有風險**<br>只要 `main` 分支有改動，線上網站會直接同步承受風險。 |
| **維護成本**     | 有新字型版號時，需更新 JSON 裡的版本號。                                             | 完全不用改 JSON。                                                     |

---

### 二、 為什麼生產環境選 `@v1.2.0` 最好？

#### 1. 享受 CDN 最高的載入速度 (Immutable Caching)

當 jsDelivr 看到 URL 裡面帶有具體版號（如 `@v1.2.0`），它知道這個檔案**永遠不會再改變**。因此全球的 CDN 節點會把這個檔案徹底快取起來，連 HTTP 304 檢查都不用做，網站開啟字型的速度是**最快、最穩定**的。

#### 2. 完全不用處理 jsDelivr 的快取延遲（Purge）

如果您用 `@main`，每次您在 GitHub 修改了 `result.css`，jsDelivr 節點最長會把舊檔案**快取長達 7 天**！使用者會在整整一星期內看到舊的字型或舊的 CSS，除非您每次改完都去呼叫 API 清快取（Purge）。

如果用 `@v1.2.0`，只要您發布 `v1.3.0` 並把 JSON 改成 `@v1.3.0`，所有使用者**瞬間就會抓到最新版**，完全沒有快取延遲問題。

---

### 三、 補充：jsDelivr 支援的「折衷神器」—— `@v1` (SemVer 語意化版本)

如果您覺得每次更新小版本（如 `v1.2.1`、`v1.2.2`）都要改一次 JSON 很麻煩，jsDelivr 支援**主版本號別名**：

可以在 `amec.json` 裡面寫：
`https://cdn.jsdelivr.net/gh/xiao-xue-seng/fonts@v1/chill-kai/result.css`

- **運作機制**：當您在 GitHub 發布了 `v1.2.0`、`v1.2.1`、`v1.3.0`，jsDelivr 的 `@v1` 都會**自動升級到最新的 `v1.x.x`**。
- **好處**：兼具了「不會被不相容的 v2 大版本改壞」的安全感，又享有「自動更新小修補 (Patch)」的方便性！

---

### 💡 總結建議

- **開發/測試階段**：`amec.json` 填寫 **`@main`**，方便您在 GitHub 上改了 CSS 就能立刻測試。
- **正式上線 (Production)**：
  1. 在 GitHub 建立一個 Git Tag 發布版本（例如 `v1.2.0`）。
  2. `amec.json` 改用 **`@v1.2.0`** 或 **`@v1`**。

_(註：別忘了我們之前在 `font-loader.js` 裡面寫好了 `normalizeFontUrl` 去重機制，就算網站 HTML 寫的是 `@v1.1.0`，而 `amec.json` 寫的是 `@v1.2.0`，去重邏輯一樣能精準識別並完美運作！)_

🟨Q：`@v1` 的效能還是會比 `@main` 好，對嗎？那麼，可以用 `@v1.2` 嗎？

---

**是的，兩題答案都是「肯定」的！**

1. **`@v1` 的效能絕對比 `@main` 好很多！**
2. **完全可以使用 `@v1.2` 這種寫法！**

以下為您說明 jsDelivr 對於 SemVer（語意化版本號）的快取機制與運作方式：

---

### 一、 為什麼 `@v1` 或 `@v1.2` 的效能會比 `@main` 好？

因為 jsDelivr 是基於 **Git Tag** 來做快取的：

- **對待 `@main`（分支）**：jsDelivr 知道分支隨時可能被 push 新內容，所以 CDN 節點會頻繁地回源伺服器檢查有沒有新 Commit，快取機制非常保守。
- **對待 `@v1` 或 `@v1.2`（SemVer 版本）**：jsDelivr 知道這背後對應的是固定的 Git Tag。雖然它會定期檢查有沒有新的 `v1.2.x` 發布，但整體 CDN 快取策略比 `@main` **穩定且快上許多**！

更重要的是，`@v1` 能**防止「破壞性改動（Breaking Changes）」**。大版本號（`v1` 到 `v2`）通常代表結構大改，用 `@v1` 能確保您的網站永遠不會被未來 `v2.0` 的大改動弄壞。

---

### 二、 jsDelivr 支援的版本號寫法全覽

jsDelivr 原生完美支援語意化版本（SemVer），您可以根據需求選擇粒度：

| 寫法範例      | 自動匹配範圍                                                     | 效能/快取表現           | 適用情境                                                      |
| :------------ | :--------------------------------------------------------------- | :---------------------- | :------------------------------------------------------------ |
| **`@v1.2.3`** | 精準鎖定此版本（不自動升級）                                     | ⚡ **最高（永久快取）** | 追求 100% 極速與絕對穩定的正式生產環境。                      |
| **`@v1.2`**   | 自動升級至最新的 **`v1.2.x`**<br>(例如自動吃 `v1.2.1`、`v1.2.2`) | 🚀 **非常高**           | **黃金平衡點！** 希望自動收到 Bug 修正，又不想跨 Minor 版本。 |
| **`@v1`**     | 自動升級至最新的 **`v1.x.x`**<br>(例如自動吃 `v1.3.0`、`v1.4.0`) | 🚀 **非常高**           | 希望自動獲得新字型功能，只要不跨主版本 (v2) 即可。            |
| **`@main`**   | 綁定 Git 最新 Commit                                             | 🐢 **較差**             | 僅適合開發與測試階段。                                        |

---

### 💡 總結建議

如果您不想每次發布 `v1.2.1` 小修正時都手動去改 `amec.json`，那麼在 JSON 裡使用 **`@v1.2`** 或 **`@v1`** 是**兼顧「CDN 高效能」與「維護便利性」的最佳選擇**！
